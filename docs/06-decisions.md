# 06. Принятые решения (лог решений / ADR)

Здесь фиксируются ответы заказчика и вытекающие из них архитектурные решения. Заменяют
соответствующие пункты в [`05-open-questions.md`](05-open-questions.md).

## D1. CRM: amoCRM + Bitrix24 (оба)

**Решение:** поддерживаем **обе** CRM через единый адаптерный интерфейс (см. [`03-interfaces.md`](03-interfaces.md) §4).
Конкретная CRM выбирается конфигурацией (`CRM_PROVIDER=amocrm|bitrix24`).

- **amoCRM** — SaaS, заточена под продажи (лиды/сделки/воронки), OAuth 2.0, вебхуки. Данные на серверах amoCRM.
- **Bitrix24** — портал «всё в одном» (CRM + задачи + телефония), REST API, вебхуки; есть **коробочная (on-prem)** версия,
  что важно, если данные нужно держать внутри КГ.

**Следствие для плана:** в E5 делаем два конкретных адаптера за общим интерфейсом; маппинг полей/этапов
для каждой CRM ведём отдельно. Тесты — против `mock-crm` + тестовых порталов обеих систем.

## D2. WhatsApp: двухрежимная абстракция (верифицированный + неверифицированный)

**Решение:** Channel Gateway получает **абстракцию WhatsApp-провайдера** с двумя реализациями за одним
контрактом (Canonical Message). Режим переключается конфигурацией (`WA_MODE=cloud_api|web_bridge`).

### Сравнение вариантов

| Критерий | Cloud API / BSP (верифицированный) | Web-bridge (неверифицированный) |
|----------|-----------------------------------|----------------------------------|
| Что это | Официальный WhatsApp Business Platform от Meta (напрямую или через BSP: 360dialog, Twilio, Gupshup, Wazzup) | Неофициальный мост через WhatsApp Web/мультидевайс (WAHA, Evolution API, Baileys, whatsapp-web.js) |
| Аккаунт | Нужен верифицированный WhatsApp Business + Meta Business verification | Обычный номер/приложение, **без верификации** |
| Запуск | Дольше (верификация бизнеса, номер, шаблоны) | Быстро (сканируешь QR — и работает) |
| Стоимость | Оплата за диалоги (conversation-based) + наценка BSP | Почти бесплатно (только хостинг) |
| Шаблоны (HSM) | Да — можно писать первым вне 24-часового окна | Нет — только в рамках активного диалога |
| Стабильность/SLA | Высокая, официально | Низкая, **риск блокировки номера** (нарушение ToS), нет SLA |
| Масштаб | Высокий | Малый/MVP/тесты |

### Когда что использовать
- **Web-bridge (неверифицированный)** — для **быстрого MVP, демо, тестов и малых объёмов**. Предупреждаем
  заказчика о рисках бана номера и отсутствии официальной поддержки.
- **Cloud API/BSP (верифицированный)** — для **продакшена**: стабильность, шаблоны, масштаб, соответствие правилам.

**Следствие для плана:** обе реализации — за одним интерфейсом провайдера. Можно стартовать на web-bridge
(M4 не блокируется доступом к Meta) и переключиться на Cloud API без изменений в остальной системе.
**Провайдер BSP пока не зафиксирован** — рекомендация по умолчанию для верифицированного режима: начать с
**WhatsApp Cloud API напрямую** (минимум посредников/наценки), при необходимости доп. функций перейти на BSP
(напр. 360dialog). Это уточняется ближе к продакшену.

## D3. Хостинг: старт на VPS + Docker Compose, миграция в облако при масштабе

**Решение:** на старте/MVP — **один VPS с Docker Compose** (соответствует self-hosted n8n и низкой стоимости).
Переход на managed-облако — когда потребуются HA, авто-масштабирование и строгий комплаенс.

### Сравнение

| Критерий | VPS (Hetzner/DigitalOcean/региональный КГ) | Managed Cloud (AWS/GCP/Azure/Yandex Cloud) |
|----------|---------------------------------------------|--------------------------------------------|
| Стоимость | Низкая и предсказуемая (фикс/мес) | Выше, оплата за множество сервисов |
| Скорость старта | Высокая (один сервер, compose) | Ниже (настройка managed-сервисов) |
| Управление | Сами: бэкапы, обновления, мониторинг | Многое managed (БД, масштаб, бэкапы) |
| Масштаб/HA | Ограничен (вертикально) | Высокий (горизонтально, multi-AZ) |
| Контроль данных | Полный; можно выбрать регион/КГ | Зависит от регионов провайдера |

**Вывод:** на этом этапе **VPS выгоднее** — дешевле, быстрее, полный контроль, идеально под Docker Compose +
self-hosted n8n. Если данные должны оставаться в КГ — берём региональный VPS (или Bitrix24 on-prem).
**Рекомендация по умолчанию:** Hetzner/DigitalOcean для скорости и цены; если критична резиденция данных в КГ —
локальный провайдер. Финально зависит от требований к персональным данным (см. вопрос о PII).

## D4. LLM: многоуровневая маршрутизация моделей через Gateway

**Решение:** не одна модель, а **тиринг через LLM Gateway** с абстракцией провайдера и фолбэком.

| Тир | Модели (референс) | Где применять | Почему |
|-----|-------------------|---------------|--------|
| Базовый (дешёвый, быстрый) | `gpt-4o-mini` / Claude Haiku | 80%+ ответов: FAQ, RAG-ответы, простые диалоги | Низкая цена и задержка при достаточном качестве — критично для модели оплаты за результат |
| Усиленный | `gpt-4o` / Claude 3.5 Sonnet | Сложные диалоги, квалификация, неоднозначные кейсы | Лучшее рассуждение там, где это окупается |
| Эмбеддинги | `text-embedding-3-small` | RAG-индексация/поиск | Дёшево и качественно |

**Почему такой выбор для этой задачи:**
- **Стоимость под контролем.** Проект оплачивается по этапам/результату; маршрутизация на дешёвый тир по
  умолчанию + кэширование минимизируют расходы на токены.
- **Качество там, где нужно.** Дорогую модель зовём только для сложных кейсов и эскалаций.
- **Без вендор-лока.** Абстракция провайдера (OpenAI + Anthropic) и фолбэк повышают надёжность и дают
  переговорную гибкость по цене.
- **Языки.** Русский оба семейства поддерживают хорошо. **Кыргызский — low-resource**, качество нужно
  проверить на оценочном наборе (E2/E1); при слабом качестве — усиленный тир + тщательные промпты/глоссарий.

> Конкретные версии моделей валидируем на момент внедрения (линейки обновляются) — архитектура от этого не зависит.

## D5. База знаний: сайт + документы Word и PDF

**Решение:** пайплайн ингеста RAG (E2) поддерживает три источника:
- **Веб-сайт** — краулер (с уважением к robots), извлечение основного контента, дедупликация.
- **Word (.docx)** — парсинг текста и структуры (заголовки/таблицы).
- **PDF** — извлечение текста (для сканов — опциональный OCR, уточнить наличие сканов).

Каждому документу — метаданные (`source`, `title`, `url/filename`, `lang`, `updated_at`) для фильтрации
и цитирования источника в ответах. Предусмотреть переиндексацию при обновлении сайта/документов.
